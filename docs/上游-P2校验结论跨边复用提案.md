# P2 校验结论跨边复用提案（上游 → 下游 publish 审核）

> 状态：**提案，待下游审核**（2026-10-07 上游起草）。
> 目标：publish 复用 xml2pdf 已产生的校验通过结论，跳过重复校验（省整轮渲染+校验）。
> 相关：`docs/校验report.json说明.md`（机读结论契约）；`docs/上游-GUI校验根参数提案.md`
> （已落地，报告可发现的前提）；publish `docs/上游-校验指纹与report.json提案.md`。

## 1 背景

同一部书常在两处各校验一次：

- **xml2pdf**：GUI 独立窗/CLI `--verify` 逐字校验，产出 `report.json`（机读结论）。
- **publish**：自制/重制选「校验」时，进程内经 bridge 调上游 CLI 再校验一遍。

两处结论不互通 → 已在上游校验通过的书，在 publish 侧仍要重跑分钟级的渲染+校验。
目标：publish 把上游 `report.json` 里 `verdict=pass` 的**指纹**导入自己的通过记录库，
现算一致即跳过（与 publish 现有「复用」机制同构）。

## 2 现状（双方代码事实，2026-10-07）

**指纹是内容哈希、无路径**（`pycbeta/verify.py`）：

- 文件标识 `_file_identity`：`{name,size,mtime_ns,sha256}`（`verify.py:2207-2220`；
  `mtime_ns` 只记录、不参与哈希）。
- 生效配置规范形 `canonical_verify_config`：只收影响文本的键（含 `theme_css`／
  `annotations`／`strip_head_no`／`title_t2s`／`scope_juan`／`bases`／`pages`），
  位置信息一律剔除（`verify.py:2301-2368`）。
- 实现摘要 `_impl_digest`：`pycbeta.__version__` + 相关模块源码哈希（改实现即失效）。
- 阈值 `{max_diff, diff_lines}` 进指纹载荷（`verify.py:2521-2539`）。
- 基线按 **basename** 参与标识 → work 布局与 fmt 布局的同名文件**指纹相同**。

**机读结论与发现**：

- `report.json` 每格式含 `verdict` + `fingerprint`（`verify.py:2762-2771`）。
- CLI/GUI 均写同名 `report.json`（2026-10-07 命名统一）；发现接口
  `find_verify_reports(verify_root)`（`verify.py:2838-2877`）只扫
  `{校验根}/*（验证）/` 直接子目录、只认 `report.json`。
- GUI 校验根已支持显式覆盖：`--verify-root` ＞ 预设 `source.verify_root` ＞
  `{输出}/验证`（`docs/上游-GUI校验根参数提案.md`，2026-10-07 落地）。

**publish 侧现状**：

- 通过记录库 `config/verify_records.json` 存上游指纹（`verify_cache.py`）；
  跳过三元 = 库有记录 + 现算一致 + 产物在库（`main_window.py:5388-5389`）。
- 指纹调用 `xml2pdf_bridge.py:1195`：`config_path=preset`（**裸预设**）。
- 上游 GUI 报告指纹用**临时 run.json**（`gui/__main__.py:385`，`config_path=tmpcfg`）。

**两处已知不一致（复用的主要障碍）**：

1. **阈值**：publish 恒传 `--verify-max-diff 5`（其配置默认 5）；上游 GUI 用预设
   `verify.maxDiff`（出厂 10）；CLI `--verify-max-diff` argparse 默认 10 且**不读预设**
   （`cli.py:740`）。阈值进指纹 → 不一致则跨边永不相等。
2. **配置形态**：上游 GUI 报告指纹用 run.json 形态（5 槽 + `config-json` → 预设），
   publish 用裸预设形态；`canonical_verify_config` 含 `theme_css`/`annotations`/
   `strip_head_no` 等，两种解析形态**大概率不等**。

## 3 方案（最小改动）

### 3.1 上游（配置 + 文档，无代码改动）

- 预设 `verify.maxDiff` 与 publish 对齐（**取值待定**，见 §8）；GUI 走预设即生效。
- 文档注明：CLI 校验须带 `--verify-max-diff <同值>`（argparse 默认不读预设）；
  且需 `--config run.json`（run 形态）才与 GUI 报告指纹同形。

### 3.2 publish（三步）

1. **指纹形态修正**：`verify_fingerprint` 改用 run 包装路径计算（与 publish 自身
   校验运行同形）；现有 `verify_records.json` 记录一次性作废（重验一次）。
2. **报告发现**：新增键 `xml2pdf.verify_reports_dir`（默认 `{xml2pdf.path}/verify`，
   即当前预设 `source.verify_root`）；经上游公开接口 `find_verify_reports` 扫
   `*（验证）/report.json`，按 JSON 内 `work` 字段匹配。
3. **入库闭环（四条件齐）**：`verdict=="pass"` + 指纹相等 + publish 产物存在
   （`find_built`）+ `formal_outputs` 非空 → `record_pass`。

## 4 优先级

- **高**：省的是整轮渲染+校验（分钟级/部），尤其 publish 自制/重制批量。
- 上游侧近乎零改动（配置+文档）；主要工作量与风险在 publish 侧（三步）。
- 前置已就绪：`report.json` 命名统一 + GUI `--verify-root`（报告可发现）。

## 5 验收

- T0001（或 X1077）双边指纹**逐字比对一致**（同预设、同阈值、同配置形态）。
- publish 复用命中：库有上游 pass 记录时**跳过渲染+校验**，产物沿用。
- `regen_all`/强制重验**不读库**（语义不变）；未命中时行为与现状一致。
- 单测：指纹形态、`verify_reports_dir` 发现、四条件入库/拒绝。

## 6 publish 影响

- 正向：已在上游验证通过的书，publish 侧免重验；报告定位稳定（`--verify-root` +
  `verify_reports_dir`）。
- 兼容：`verify_records.json` 一次性作废仅导致**多跑一次**校验，无数据损失；
  未配置 `verify_reports_dir` 时功能等价现状（不导入）。

## 7 风险与前提

- 首选基线缺失时指纹为 `None`（`verify.py:2507`）→ 不会命中，安全重验。
- 生效预设文本键不一致 → 永不命中（静默，只多一次预检）；需按 §5 实测确认。
- `impl` 含上游代码版本，升级自动失效（安全网）。
- 跨机器不主张可比（官方口径：指纹本机有效）。

## 8 开放问题（留待下游审核）

1. **阈值对齐取值/方向**：对齐到 publish 现值 5（更严）还是上游现值 10（更松）？
   或由下游在审核时定。（阈值进指纹，必须两处一致。）
2. **配置形态对齐方式**：若 §3.2 的「publish 改用 run 包装」成本或副作用不可接受，
   是否有更简方案（如上游 GUI 报告改用裸预设形态计算指纹）。
3. **入库来源**：只从上游 `report.json` 导入（不信任直写），是否需要额外校验
   `formal_outputs` 与 publish 产物的对应关系。
